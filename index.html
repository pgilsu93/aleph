01 · 로그 이상탐지 연구

로그에서 무엇이 이상을 설명하는 정보인지 살펴봤습니다.

로그의 발생 시간 간격, 짧은 시간에 로그가 집중되는 정도, 로그 레벨처럼 운영 상황을 설명할 수 있는 정보를 정리하고, 기존 모델이 충분히 사용하지 못하던 특징을 그래프 구조와 가중치에 반영하도록 다시 설계했습니다.

확인한 점
여러 특징을 따로 비교했을 때 시간 정보는 서로 다른 로그 데이터에서도 공통적으로 성능 개선에 기여했습니다.

실험에서 확인한 내용

로그가 발생한 순서만 보는 대신, 발생 시점과 빈도, 중요도를 모델이 구분할 수 있도록 여러 특징을 기존 그래프 표현에 추가해 비교했습니다.

  • 시간 간격 가까운 시간에 발생한 로그의 관계를 더 강하게 반영했으며, BGL·Thunderbird·HDFS에서 공통적으로 F1이 개선됐습니다.
  • Burst 짧은 구간에 로그가 집중되는 정도를 별도 신호로 반영했고, 특히 Thunderbird에서 높은 효과를 확인했습니다.
  • 로그 레벨 INFO·WARN·ERROR처럼 로그가 가진 중요도 정보를 연결 관계의 가중치에 포함해 시간 정보와 다른 성격의 신호로 비교했습니다.

01 · 로그 이상탐지 연구

로그의 내용뿐 아니라
발생 방식도 정보로 보기

시간적 특성을 이용한 Log-Entity Graph 개선

로그 이상탐지를 공부하면서 로그 메시지의 내용과 발생 순서뿐 아니라 언제 발생했는지, 얼마나 짧은 시간에 몰렸는지, 어떤 중요도를 가진 로그인지 역시 시스템 상태를 설명하는 중요한 정보라고 봤습니다.

예를 들어 같은 로그 조합이라도 수십 분 동안 천천히 발생한 경우와 몇 초 안에 반복적으로 쏟아진 경우는 운영 상태가 다를 수 있습니다. ERROR와 INFO가 같은 의미를 갖는 것도 아닙니다. 하지만 기존 모델에서는 이런 차이가 로그 간 연결 관계에 직접적으로 충분히 반영되지 않았습니다.

그래서 세 가지 정보를 나누어 봤습니다.

시간 간격

두 로그가 가까운 시간에 발생했는지를 연결 관계의 강도에 반영했습니다.

발생 집중도

짧은 시간 동안 로그가 반복적으로 몰리는 burst 현상을 별도 정보로 반영했습니다.

로그 레벨

INFO, WARN, ERROR 등의 중요도를 이용해 같은 연결도 서로 다르게 다룰 수 있게 했습니다.

각각의 정보를 기존 Log-Entity Graph의 연결 관계에 가중치로 사용할 수 있도록 구성하고, 특징을 개별적으로 적용했을 때와 여러 특징을 함께 적용했을 때를 비교했습니다.

여기서 관심을 둔 것은 어떤 설정 하나가 특정 데이터에서 가장 높은 점수를 냈는지가 아니라, 어떤 정보가 데이터가 바뀌어도 계속 의미 있는 신호로 작동하는지 였습니다.

실험 결과, 로그 사이의 시간 정보를 반영한 방법은 BGL, Thunderbird, HDFS 모두에서 F1을 개선했습니다. 데이터마다 효과가 큰 세부 방법은 달랐지만, 시간적 관계 자체는 세 데이터에서 공통적으로 개선을 보여 비교적 강건하게 활용할 수 있는 정보라는 결론을 얻었습니다.

02 · 웹 시스템 유지보수

화면의 문제를
화면에서만 찾지 않기

운영 시스템의 요구사항 반영과 장애 원인 추적

웹 시스템 유지보수 업무에서는 사용자의 변경 요청을 받아 화면과 비즈니스 로직을 수정하고, 필요한 데이터를 조회·처리하는 SQL을 함께 다뤘습니다.

운영 중 보이는 현상만으로는 실제 수정 지점을 바로 알기 어려운 경우가 많았습니다. 화면의 값이 잘못 보이더라도 원인이 화면 코드에 있을 수도 있고, 서버의 처리 조건이나 SQL, 저장된 데이터 상태에 있을 수도 있기 때문입니다.

그래서 요청이나 장애를 확인할 때 먼저 사용자가 어떤 동작을 했고 어느 시점에서 기대한 결과와 달라졌는지를 확인한 뒤, 해당 요청이 지나가는 로직과 SQL을 따라갔습니다. 오류가 있는 경우에는 애플리케이션 로그를 함께 보면서 실제로 문제가 발생한 지점을 좁혔습니다.

수정할 위치를 찾은 뒤에도 요청된 화면만 정상적으로 보이는지 확인하는 데서 끝내지 않았습니다. 같은 로직이나 데이터를 사용하는 기능을 함께 살펴보고 변경으로 인해 기존 동작이 달라질 가능성이 있는 부분을 확인했습니다.

이 경험을 통해 사용자의 요청을 화면 수정 하나로 받아들이기보다 화면 → 서버 로직 → SQL → 데이터 → 로그가 연결된 하나의 흐름으로 이해하는 방식 이 익숙해졌습니다. 이후 로그 이상탐지를 연구주제로 선택한 것도 시스템에서 발생한 현상을 기록을 통해 추적해 왔던 경험과 연결되어 있습니다.

03 · 학습과 설명

알고 있는 내용을
가르칠 수 있게 다시 정리하기

Java 동아리와 AI 교육과정에서의 학습 경험

대학교 4학년 때 Java 프로그래밍을 어려워하는 학생들이 많아 학과에서 Java 동아리가 만들어졌고, 요청을 받아 다른 학생과 교대로 한 학기 동안 수업을 진행했습니다.

혼자 코드를 작성할 때 알고 있다고 생각했던 내용도 다른 사람에게 설명하려고 하면 어느 부분을 정확히 이해하지 못했는지가 드러났습니다. 그래서 수업 전에 내용을 다시 확인하고, 개념을 먼저 설명한 뒤 짧은 코드 예제를 보고 직접 작성해보는 흐름으로 정리했습니다.

한 번 설명하고 넘어가는 것보다는 배운 내용을 직접 사용해 볼 수 있도록 간단한 예제와 연습 문제를 구성하고, 질문이 많이 나온 부분은 다음 설명에서 순서나 예시를 바꾸는 방식으로 보완했습니다.

이후 AI 교육과정에서도 비슷한 방식으로 공부했습니다. 제가 먼저 이해한 부분은 주변 교육생에게 설명했고, 코드 오류가 발생하면 정답 코드를 바로 전달하기보다 어느 단계에서 예상과 다른 값이 나오는지 함께 따라가며 원인을 찾았습니다.

이런 과정을 반복하면서 새로운 내용을 배울 때 단순히 한 번 실행해 보는 것보다 원리를 제 방식으로 다시 정리하고, 다른 사람에게 설명하거나 다시 적용할 수 있는 상태까지 만드는 것 을 중요하게 생각하게 됐습니다. AI 교육과정은 우수상을 받으며 수료했습니다.

이런 방식이 잘 맞습니다.

앞의 경험을 거치며 자연스럽게 반복하게 된 방식들입니다.

먼저 구조를 이해합니다.

눈앞의 현상만 바로 고치기보다 앞뒤에서 어떤 과정이 연결되어 있는지 확인한 뒤 수정할 지점을 정하는 편입니다.

다른 조건에서도 다시 확인합니다.

한 번 잘된 결과만으로 판단하기보다 조건이 달라져도 같은 설명이 가능한지 비교하면서 결과의 범위와 한계를 함께 보려고 합니다.

이해한 것은 다시 정리합니다.

새로운 내용을 배운 뒤 원리와 순서를 제 방식으로 다시 설명해 보거나 직접 적용하면서 빠진 부분을 확인합니다.
